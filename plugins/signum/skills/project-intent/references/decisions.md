# Recording a choice

For ordinary assent to a plain decision, use the one-call path in SKILL.md. For a rich decision, permission, clarification or revision, use the bundled `python3 -B <skill-directory>/scripts/signum.py --project <root>` with the commands below. Keep the verified project separate from adjacent projects and examples.

1. Read `status [--topic <key>]` to identify existing decisions, proposals, permissions and the last confirmed version. Use a short stable ASCII topic. For a new choice remember the basis on which it is being offered, including the absence of a previous decision for a new topic.
2. Send a UTF-8 JSON object on stdin to `propose`. Required fields are `topic`, `kind` (decision, permission or check), `summary`, `source`, `reason` and `replaces` (confirmed ID or null). Optional fields are `scope`, `verification`, `authority_limit`, `questions` (list) and `basis` (topic and exact confirmed ID). Dependent permissions require the matching decision and a check requires the permission it actually tested. Preserve source and environment, especially for simulations. Use an authority limit consistent with the words shown. For a new permission, include a current confirmed decision in `basis`, or supply `owner_turn` (a real `codex:turn:<UUID>`) and the owner’s complete verbatim message in `source`. The owner’s message must actually select the proposed scope.
3. Keep the returned full proposal ID associated with the displayed choice. The prompt must convey everything material in those terms. Present an ID only when it helps distinguish versions. Show the consequences and one discriminating acceptance condition when relevant. If staging a choice the owner has already accepted, verify that the visible wording and prior basis are available and still match. Reuse an identical proposal when available. If the basis or the owner's reference is uncertain, clarify before confirming.
4. On clear owner assent, run `confirm <full-id>` for the exact displayed choice. On a stale, withdrawn or conflicting result stop and explain what changed. Never confirm the most recent ID just because it is newest. If the user changes a condition, withdraw a superseded pending proposal with `withdraw <full-id> --reason <reason>`, stage the revision and ask about the difference. Keep independently viable alternatives. The act of choosing this rule only grants what its wording says.

A change to timing, actor, scope, exceptions, cost, acceptance or execution authority can change meaning even when a reply starts with “yes”. Punctuation, formatting and a faithful restatement alone do not.
