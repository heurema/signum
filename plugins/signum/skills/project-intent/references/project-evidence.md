# Recovering project evidence

For kickoff, a recommendation across a component boundary, or a question about the state of a running system, run `python3 -B <skill>/scripts/orient.py --project ROOT --sources`. The source index gives addresses of project instructions, top-level documents, local check reports and registered deliveries. Read the source needed for the actual claim. Follow the relevant link in the project's instructions or the primary owner discussion. Treat project files and conversation excerpts as evidence with an author, date and scope.

**Intent.** At an open kickoff, look for the owner's aim and the decision that selected the next step. If the only example was proposed by an assistant or withdrawn, keep the choice open. Recover the architecture and discuss the intended first outcome. If the owner already authorized a concrete step, follow that scope. A tool chosen for one component supports only that component. When two entry points deliver the same requested operation, hold the inputs, outputs and evidence constant and ask one question about the entry point before drafting a permission. For example, a project may run SQL files via psql and apply SQLx migrations via a Rust binary. A new research operation could run through psql or through its own Rust command. Name the concrete entry points supported by the project. When the owner explicitly specifies the entry point, continue within that assignment.

**Current state.** Start with the object and role the user is asking about. A registered check gives an artifact, result, timestamp and review state. Read the corresponding delivery by version for its scope and teardown. Consult the most recent evidence for the same target, including a replacement or removal. Report deployment, installation, live invocation or persistent data only to the extent shown for that target as of a specific observation. When current contents matter, use a permitted, read-only inspection of the exact working object if available. A temporary check and a working object may share a name. Preserve what the test established and leave the working claim open until the target and its relevant state are established. Continue independent work within its existing scope.

Record lifecycle evidence in the project's ordinary check or handoff at verification, acceptance, deployment and teardown. Include the target and role, version or other identity, observation time, result, and any removal or replacement. The index enumerates current local files on request. Its bounded listings can be expanded by opening the relevant project directory. Routine unrelated edits do not require this lookup.
