# Delivering an agreed change

Use the same package version and `signum.py --project <project-directory>` entry point.

1. Obtain the confirmed permission ID and its literal verification criteria from `contract --topic <topic>`. Run `start <permission-id>` before work. For an exact file scope, run in a small isolated copy, supply intended edits with repeated `--touch PATH`, and keep the check report at the exact new path in the contract. The scope check compares the persistent state of that copy at recorded steps. Commands run with their usual filesystem access. Existing dirty files are included in the baseline. Keep temporary outputs outside the copy and use Python `-B` when appropriate. Only legacy permissions can use an externally observed start via `--started-at <UTC> --source <observation>`. Give the executor the scope, verification criteria and authority limits. Check the current contract again before applying a changed requirement.
2. Implement within scope. Immediately before checking, run `snapshot <changed-paths...>` (add `--deleted <path>` for a removed file). Keep the returned `files`. Run the agreed checks on those bytes and save their actual outputs or a compact, inspectable account in a project-local UTF-8 file. For multiple criteria make each observation and gap identifiable. An incomplete or failed result uses `status: fail`. Measure elapsed time; collect input/output tokens when the executor reports them. Distinguish waiting from active work and cache hits from total input. Leave unobserved costs unknown.
3. Run `verify --report <agreed-new-project-relative-path> --name <label> -- <command> <args...>` to record the command's exit code and elapsed time. For a pass under a new exact file scope, use the report produced by `verify` for the active start and the matching implementation snapshot. Run multiple agreed checks through one command that exits nonzero if any required check fails. Keep the observations and gaps in the result. Existing contracts can also use an aggregated JSON report with a nonempty `checks` array of named observations with zero integer exit codes. Run `snapshot --artifact <report-path>` on the finished report. Send a JSON object on stdin to `evidence <permission-id>` containing the original `files` snapshot, the returned `artifact` object, `criteria` (exact text), `result` (observed outcome), and `status` (`pass` or `fail`). An optional `checked_at` is a UTC timestamp and must match the bound report when supplied for a pass. Optional `measurements` holds any measured `elapsed_seconds`, `input_tokens`, `output_tokens` and a required `source`. Save the report outside the project's root `.git` and `.signum` directories. For a retry on the same scoped contract, preserve your failed report outside the working copy, free its agreed path, and run the check again on a fresh snapshot. A changed snapshot requires checking the new bytes. The core only executes commands explicitly supplied to `verify`.
4. Show the owner the exact version from `delivery <id>`, outcome, gaps, time, and link to the evidence. Group independent results for one review when useful. Proceed with `accept <id> --source <owner statement> --reason <reason>` or `return <id> --source <owner statement> --reason <reason>` only after the owner decides on that displayed result. A reviewer or green check cannot accept on their behalf. A changed result needs a new version and review. An accepted local result carries no authority to release.

## Continue a delivery investigation

Run `python3 -B <skill-directory>/scripts/resume_delivery.py --project <current project> --rehearse`. Add `--id <ID>` for a specific proposal. If reading this skill on the first turn, read it and run the command together. This single operation looks up current local records, checks the proposed source against the accepted digest, rehearses in a disposable directory and verifies the resulting delivery evidence.

When the owner explicitly selects both listed repairs together under the project's choice rules, add `--pair <ID1> <ID2>` using both complete IDs. The two IDs must match the entire current choice for one delivery and refer to distinct paths. The pair uses the recorded sources and checks both files together on one disposable copy. `--id` and `--source` are for the single-repair flow.

Answer from the receipt. For `ready`, report the trial’s `healthy`, `degraded` (remaining findings or blockers) or `blocked` result and the remaining owner decision. If a source file is needed, a known path can be supplied with `--source /absolute/file`. A trial never repairs the working project. For `ambiguous`, ask one question listing the distinguishing files or deliveries and use the chosen ID on the next call. For `none` or `unknown`, explain the observed outcome.
